⏺ That's a great catch. The answer is:

  The track.yaml file is stale/out-of-sync with the sprint files.

  The track.yaml has manually-maintained sprint summaries:
  sprints:
  - id: sqlite-backend-2
    status: not_started  # ← WRONG
  - id: sqlite-backend-3
    status: not_started  # ← WRONG

  But the actual sprint.yaml files say:
  - sqlite-backend-2: status: completed
  - sqlite-backend-3: status: completed

  Why the round-trip test passed:

  The test loaded data from YAML → SQLite → YAML → SQLite and compared the two SQLite databases. Both databases were built
  from the same YAML source files, so they matched perfectly.

  The test verified serialization integrity (no data loss during conversion), not data consistency (whether parent summaries
  match child statuses).

  This is exactly the problem SQLite is supposed to solve - the track.yaml has embedded sprint summaries that drift out of
  sync with the actual sprint files. With SQLite + computed views, the track's sprint list would be a JOIN query, not a
  manually-maintained copy.

  This inconsistency exists because someone updated the sprint.yaml files but didn't update the track.yaml's embedded sprint
  summaries. Classic state drift.
